## データの流れ

```
   [受付・看護師]              [医師]                    [患者さん]
        │                       │                          │
   ① 入力 ──────────────────────┤                          │
        │                       │                          │
        ▼                       ▼                          │
   Session（メモリ内）──→ logic/*.ts で判定 ──→ 判定パネル     │
        │                                                   │
        │                  ② 説明                            │
        ├──→ slides/*.tsx（患者データを図に反映）──────────────→ 説明画面
        │                                                   │
        │                  ③ 方針                            │
        ├──→ plan（薬・運動処方・生活指導・次回）               │
        │         │                                         │
        │         ├──→ ② のスライドに反映（薬・運動のページが増える）
        │         │                                         │
        │         ├──→ ④ Pamphlet.tsx ──→ 印刷 ──────────────→ パンフレット
        │         │                                         │
        │         └──→ ⑤ karte.ts ──→ カルテ文・算定候補 ──→ 電子カルテ
        │
        └──（任意）server/ に実施記録（氏名なし・受付番号はハッシュ）
```

**一度入力したものを二度入力しない**ことが、このシステムの効率化の中心です。
薬を選ぶと、説明スライド・パンフレット・カルテ文・算定候補・検査候補・次回来院候補が
すべて連動して変わります。

## 設計判断とその理由

### なぜ図をすべて手描きのSVGにしたか

| 案 | 却下した理由 |
| --- | --- |
| 画像ファイル（PNG/JPEG） | 拡大すると粗くなる。印刷で汚くなる。患者データを反映できない |
| 外部の医療イラスト素材 | ライセンスの制約。オフラインで使えない場合がある。統一感が出ない |
| Canvas / 描画ライブラリ | 印刷時の解像度が落ちる。テキストが選択・読み上げできない |

**採用：手描きSVGコンポーネント**
- 拡大・印刷でも劣化しない（診察室の大画面でもA4印刷でも同じソースを使える）
- `yam` や `tier` を props で受け取り、**患者ごとに図が変わる**
- 外部依存ゼロ。オフラインの院内PCで確実に動く
- `<title>` / `<desc>` を持たせているため読み上げにも対応できる
- 色覚バリアフリーを意識し、赤緑の対比だけに情報を持たせていない（形・位置・文字を併用）

### なぜ PDF ライブラリを使わずブラウザ印刷にしたか

jsPDF や pdf-lib で日本語PDFを作るには、日本語フォントの埋め込み（数MB）が必要で、
フォントのライセンス・サブセット化・縦書き・ルビなどでつまずきます。
**ブラウザの印刷機能は日本語を確実に扱え、どの端末でも同じ結果になり、
「PDFに保存」も同じボタンでできます。** 診察室では印刷が目的なので、これが最短です。

`@page { size: A4 portrait }` と `break-after: page` で、画面のA4プレビューと紙面を一致させています。

### なぜ状態管理ライブラリを使わなかったか

診察1件分の状態は1つの `Session` オブジェクトに収まり、画面遷移も5ステップの一方向です。
Redux/Zustand を入れる複雑さに見合う利点がないため、
**React Context + `useState`** にしています（`src/state/store.tsx`、約150行）。

### なぜ患者情報を既定で保存しないか

説明支援ツールに患者情報を蓄積する必然性がありません。
保存しなければ、端末紛失時の影響も、削除運用も、監査の負担も小さくなります。
「一時保存」は `sessionStorage`（タブを閉じると消える）に限定し、
`localStorage` には患者情報を書きません。

構成Cで記録を残す場合も、氏名は受け取らず、受付番号はソルト付きハッシュ、
年齢は5歳刻みの年齢層にしています。集計と継続管理に必要な最小限だけを持ちます。

### なぜ診療報酬の点数をコードに置いたか

改定ごとの変更履歴を Git で追えるようにするためです。
設定画面から編集できる形にすると「いつ誰が何を変えたか」が失われます。
点数は算定に直結するため、**変更が記録される場所に置く**判断をしました。

未確認の項目は `points: null` とし、画面に「要確認」と表示されます。
**推測で数字を埋めない**ことを設計で強制しています。

### なぜ「立てない」と「未実施」を型で分けたか

ロコモ度の立ち上がりテストで、両者を `null` で表すと
**未実施を「最重症」と誤判定します。**
`StandUpResult = number | 'cannot' | null` として型で区別し、
入力画面でもボタンを分け、テストで両方の挙動を固定しました。

開発中、テストがこの誤りを実際に検出しています。
同様に ACR/EULAR 2010 分類基準の階層（10か所超＝5点を先に判定する）の
取り違えもテストが検出しました。

### なぜ医師用トークスクリプトを画面に置いたか

説明の質が医師によってばらつくのが、患者説明の最大の課題です。
各スライドに「この画面で伝えること」を置くことで、
**研修医・非常勤医でも同じ水準の説明ができる**ようにしています。
患者さんに画面を渡すときはワンタップで非表示にできます。

### なぜ疾患を3つに絞ったか

整形外科クリニックで「説明に時間がかかり、かつ説明の質が治療成績に直結する」領域を選びました。
骨粗鬆症と関節リウマチは**継続率が成績を決める**疾患であり、
膝OA・ロコモは**運動療法が治療の中心**である疾患です。
いずれも当院の特色である運動療法への導入と直結します。

疾患の追加手順は [05_カスタマイズガイド.md](05_カスタマイズガイド.md) の第6節にあります。

## テスト方針

`src/logic/` の臨床判断ロジックだけを対象にしています（111件）。

| ファイル | 件数 | 対象 |
| --- | --- | --- |
| `osteoporosis.test.ts` | 33 | YAM↔T換算、低い方の採用、診断基準の全分岐、開始基準の全分岐、リスク層別化、検査値の注意 |
| `ra.test.ts` | 27 | DAS28-ESR/CRP の原式（手計算値と照合）、SDAI/CDAI、Boolean寛解、ACR/EULAR2010、T2Tコメント |
| `locomo.test.ts` | 28 | ロコモ度の3テストと総合判定、「立てない／未実施」の区別、BMI・減量目標・膝への負荷 |
| `karte.test.ts` | 23 | カルテ文の生成内容、算定候補の条件分岐、検査候補の並び、次回来院候補 |

UIのスナップショットテストは、意図的に入れていません。
図表とレイアウトは**実際にA4へ印刷して目視で確認**するのが唯一確実な検証方法であり、
スナップショットは変更のたびに更新が必要になって形骸化しやすいためです。
開発時は Playwright で印刷PDFを生成して確認しています（手順は
[05_カスタマイズガイド.md](05_カスタマイズガイド.md) の第5節）。

## 依存パッケージ

意図的に最小限にしています。

| パッケージ | 用途 | 代替を検討したが却下した理由 |
| --- | --- | --- |
| `react` / `react-dom` | UI | — |
| `qrcode` | パンフレットのQRコード | 外部APIでの生成はオフラインで使えない |
| `vite` / `@vitejs/plugin-react` | ビルド | — |
| `tailwindcss` | スタイル | 印刷用CSSと画面用CSSを1か所で管理できる |
| `typescript` | 型 | 臨床データの取り違えを型で防ぐため必須と判断 |
| `vitest` | テスト | — |
| `better-sqlite3`（server のみ） | 保存 | PostgreSQL/MySQL は院内サーバー1台の運用に対して過剰 |

**含めていないもの**：HTTPクライアント、状態管理ライブラリ、UIコンポーネントライブラリ、
チャートライブラリ、PDFライブラリ、分析タグ、エラー収集サービス。
外部への通信が発生しないことを保証するためです。
