## データの流れ

```
   [受付・看護師]              [医師]                    [患者さん]
        │                       │                          │
   ① 入力 ──────────────────────┤                          │
        │                       │                          │
        ▼                       ▼                          │
   Session（メモリ内）──→ logic/*.ts で判定 ──→ 判定パネル     │
        │                                                   │
        │                  ② 説明                            │
        ├──→ slides/*.tsx（患者データを図に反映）──────────────→ 説明画面
        │                                                   │
        │                  ③ 方針                            │
        ├──→ plan（薬・運動処方・生活指導・次回）               │
        │         │                                         │
        │         ├──→ ② のスライドに反映（薬・運動のページが増える）
        │         │                                         │
        │         ├──→ ④ Pamphlet.tsx ──→ 印刷 ──────────────→ パンフレット
        │         │                                         │
        │         └──→ ⑤ karte.ts ──→ カルテ文・算定候補 ──→ 電子カルテ
        │
        └──（任意）server/ に実施記録（氏名なし・受付番号はハッシュ）
```

**一度入力したものを二度入力しない**ことが、このシステムの効率化の中心です。
薬を選ぶと、説明スライド・パンフレット・カルテ文・算定候補・検査候補・次回来院候補が
すべて連動して変わります。

## 設計判断とその理由

### なぜ図をすべて手描きのSVGにしたか

| 案 | 却下した理由 |
| --- | --- |
| 画像ファイル（PNG/JPEG） | 拡大すると粗くなる。印刷で汚くなる。患者データを反映できない |
| 外部の医療イラスト素材 | ライセンスの制約。オフラインで使えない場合がある。統一感が出ない |
| Canvas / 描画ライブラリ | 印刷時の解像度が落ちる。テキストが選択・読み上げできない |

**採用：手描きSVGコンポーネント**
- 拡大・印刷でも劣化しない（診察室の大画面でもA4印刷でも同じソースを使える）
- `yam` や `tier` を props で受け取り、**患者ごとに図が変わる**
- 外部依存ゼロ。オフラインの院内PCで確実に動く
- `<title>` / `<desc>` を持たせているため読み上げにも対応できる
- 色覚バリアフリーを意識し、赤緑の対比だけに情報を持たせていない（形・位置・文字を併用）

### なぜ PDF ライブラリを使わずブラウザ印刷にしたか

jsPDF や pdf-lib で日本語PDFを作るには、日本語フォントの埋め込み（数MB）が必要で、
フォントのライセンス・サブセット化・縦書き・ルビなどでつまずきます。
**ブラウザの印刷機能は日本語を確実に扱え、どの端末でも同じ結果になり、
「PDFに保存」も同じボタンでできます。** 診察室では印刷が目的なので、これが最短です。

`@page { size: A4 portrait }` と `break-after: page` で、画面のA4プレビューと紙面を一致させています。

### なぜ状態管理ライブラリを使わなかったか

診察1件分の状態は1つの `Session` オブジェクトに収まり、画面遷移も5ステップの一方向です。
Redux/Zustand を入れる複雑さに見合う利点がないため、
**React Context + `useState`** にしています（`src/state/store.tsx`、約150行）。

### なぜ患者情報を既定で保存しないか

説明支援ツールに患者情報を蓄積する必然性がありません。
保存しなければ、端末紛失時の影響も、削除運用も、監査の負担も小さくなります。
「一時保存」は `sessionStorage`（タブを閉じると消える）に限定し、
`localStorage` には患者情報を書きません。

構成Dで記録を残す場合も、氏名は受け取らず、受付番号はソルト付きハッシュ、
年齢は5歳刻みの年齢層にしています。集計と継続管理に必要な最小限だけを持ちます。

### なぜ診療報酬の点数をコードに置いたか

改定ごとの変更履歴を Git で追えるようにするためです。
設定画面から編集できる形にすると「いつ誰が何を変えたか」が失われます。
点数は算定に直結するため、**変更が記録される場所に置く**判断をしました。

未確認の項目は `points: null` とし、画面に「要確認」と表示されます。
**推測で数字を埋めない**ことを設計で強制しています。

### なぜ「立てない」と「未実施」を型で分けたか

ロコモ度の立ち上がりテストで、両者を `null` で表すと
**未実施を「最重症」と誤判定します。**
`StandUpResult = number | 'cannot' | null` として型で区別し、
入力画面でもボタンを分け、テストで両方の挙動を固定しました。

開発中、テストがこの誤りを実際に検出しています。
同様に ACR/EULAR 2010 分類基準の階層（10か所超＝5点を先に判定する）の
取り違えもテストが検出しました。

### なぜ設定・資料集から「診察の続き」に戻るようにしたか

設定や資料集を開いたあと最初の画面に戻す実装にしていたところ、
**診察の途中で点数や基準を確認しただけで、入力画面まで戻り直す必要がありました。**
診察室では数十秒でも致命的です。

`go()` が設定・資料集へ移るときだけ直前の画面を覚え、`goBack()` でそこへ戻します。
戻るボタンの文言も「← 診察の続きへ戻る」に変わり、どこへ戻るかが分かるようにしています。

### なぜ Field に `group` を用意したか

`<label>` で包めるのは入力欄だけです。ボタンの並び（`SegButton`・チップ）を
`<label>` で包むと、読み上げソフトが**見出しと選択肢すべてを1つのボタン名として読み上げます**。

`Field` に `group` を付けると `role="group"` + `aria-labelledby` になり、
各ボタンは自分の文言だけを名前として持ちます。
（この誤りは、ブラウザ操作テストが「CRP調整基準」のボタンを一意に特定できないことで見つかりました。）

### なぜ医師用トークスクリプトを画面に置いたか

説明の質が医師によってばらつくのが、患者説明の最大の課題です。
各スライドに「この画面で伝えること」を置くことで、
**研修医・非常勤医でも同じ水準の説明ができる**ようにしています。
患者さんに画面を渡すときはワンタップで非表示にできます。

### なぜ「連携」をラベル解析にしたか

電子カルテとの直接連携（HL7 FHIR、SS-MIX2、ベンダーAPI）は、
施設ごとにベンダー・バージョン・契約が異なり、導入のたびに開発が必要になります。
一方で、**問診システムの結果もカルテの検査値も、画面には文字として出ています。**

そこで「画面の文字を貼り付ける」ことを一次手段にしました。

- 相手のシステムを問わず、**今日から使えます**
- 相手の出力形式が変わっても、ラベルさえ残っていれば動きます
- 誤読のリスクは、**必ず確認画面を挟む**ことで抑えています

ラベルの解析では、次の2点が壊れやすいので明示的に対処しています。

1. **部分一致の誤読**：`DAS28-CRP` を `CRP` として読んでしまう問題。
   定義を「specificな順」に並べ、一度マッチした文字範囲を消費済みにして
   後続の定義が再マッチしないようにしています（`consumed` 配列）。
2. **かっこ書き**：`患者全般評価（VAS）：5.0` のように単位や補足が挟まる書き方。
   ラベルと値のあいだに1つだけかっこ書きを許す正規表現にしています。

どちらも、実際にテストが誤読を検出したうえで直しています。

URL連携も用意しましたが、**URLに患者データが載る**という弱点があるため、
読み込み直後に `history.replaceState` でURLから消し、
アクセスログに残る可能性を設定画面で明示しています。

### なぜ問診システムだけは直接読み込みにしたか

貼り付けを一次手段にしたうえで、院内のデジタル問診システム（`monshin-tablet`）については
API から直接読み込む経路（`logic/monshin.ts`）を足しました。相手が特定できているためです。

- 患者さんが**タブレットで答えた内容**（mHAQ 8項目・全般評価VAS・こわばり・前回比）は、
  医師の画面には一覧でしか出ないため、貼り付けでは拾えません
- 一方、関節数・CRP・SDAI は**医師がブラウザ内で入力する値**でサーバーには無いため、
  API では拾えず、貼り付けが必要です

つまり両者は排他ではなく**補完関係**にあり、続けて実行すると手入力がゼロになります。
UI 側も、取り込み完了のバナーから貼り付け画面へ直接進めるようにしてあります。

実装上の制約として、次を守っています。

- **相手のプログラムを1行も変更しない**（読み取り専用の `GET` のみ・書き込みAPIは呼ばない）
- 既定のURLは**空文字＝同一オリジン**。同じフォルダに置けば設定不要で、CORS も発生しません
- `credentials: 'omit'` / `cache: 'no-store'` / 4秒でタイムアウト。
  問診システムが落ちていても診察を止めない（失敗したら貼り付けに誘導する）
- 取り込む前に**必ずプレビュー**を出す

### なぜ DAS28-CRP のカットオフを設定可能にしたか

院内の問診システムと突き合わせたところ、**計算式は完全に一致していたのに、
DAS28-CRP の活動性区分だけが食い違う**ことが分かりました。

| | 寛解 | 低 | 中 | 高 |
| --- | --- | --- | --- | --- |
| 慣用基準（DAS28-ESR 由来） | <2.6 | ≦3.2 | ≦5.1 | >5.1 |
| CRP調整基準 | <2.3 | <2.7 | ≦4.1 | >4.1 |

DAS28-CRP は DAS28-ESR より低く出るため、ESR 用の区分をそのまま当てると
活動性を低く見積もることが知られています。一方で慣用基準を使う施設も多くあります。
どちらか一方を「正解」として実装すると、**同じ患者の同じ値が2つの画面で違う区分になり**、
診察室での説明が破綻します。

そこで `ClinicalSettings.das28crpThresholds` として設定に出し、
**既定を院内の問診システムと同じ「慣用基準」**にしました。
画面には採用中の区分値を常時表示し、設定画面には
「変更するときは問診システム側も合わせること」を注意として出しています。

臨床上の基準の当否より、**2つの画面が食い違わないこと**を優先した判断です。

### なぜ取り込んだスコアと計算値を突き合わせるか

問診システムの SDAI をそのまま信用して表示することもできますが、
**転記ミスや単位違い（VASのcm/mm、CRPのmg/dL・mg/L）は実際に起こります。**

内訳が揃っていれば本システムで再計算し、取り込み値と食い違えば警告を出します。
これは「二重チェック」として機能し、システムを入れる前より安全になります。
内訳が無い場合は取り込み値をそのまま使い、その旨をカルテ記載にも残します。

### なぜ疾患を3つに絞ったか

整形外科クリニックで「説明に時間がかかり、かつ説明の質が治療成績に直結する」領域を選びました。
骨粗鬆症と関節リウマチは**継続率が成績を決める**疾患であり、
膝OA・ロコモは**運動療法が治療の中心**である疾患です。
いずれも当院の特色である運動療法への導入と直結します。

疾患の追加手順は [05_カスタマイズガイド.md](05_カスタマイズガイド.md) の第8節にあります。

## テスト方針

`src/logic/` の臨床判断ロジックと取り込み処理を対象にしています（213件）。

| ファイル | 件数 | 対象 |
| --- | --- | --- |
| `osteoporosis.test.ts` | 33 | YAM↔T換算、低い方の採用、診断基準の全分岐、開始基準の全分岐、リスク層別化、検査値の注意 |
| `ra.test.ts` | 43 | DAS28-ESR/CRP の原式（手計算値と照合）、SDAI/CDAI、Boolean寛解、ACR/EULAR2010、T2Tコメント、取り込み値との突き合わせ、**院内問診システムとの計算式一致とカットオフ設定** |
| `locomo.test.ts` | 28 | ロコモ度の3テストと総合判定、「立てない／未実施」の区別、BMI・減量目標・膝への負荷 |
| `karte.test.ts` | 23 | カルテ文の生成内容、算定候補の条件分岐、検査候補の並び、次回来院候補 |
| `importer.test.ts` | 43 | ラベル解析、紛らわしいラベルの取り違え防止、表記ゆれ、単位換算、範囲外の除外、セッションへの反映 |
| `monshin.test.ts` | 27 | 問診回答のマッピング（VAS換算・mHAQ平均・こわばり・前回比）、警告の引き継ぎ、診察室画面の出力の貼り付け |
| `urlParams.test.ts` | 16 | URL連携の全パラメータ、表記ゆれ、不正値の除外、見本URLの往復 |

`ra.test.ts` の「問診システムと計算式が一致すること」は、
院内問診システム（`js/doctor.js`）の実装をそのまま移した参照実装と本システムの出力を
突き合わせるテストです。**どちらかを直したときに食い違いが検出されます。**

UIのスナップショットテストは、意図的に入れていません。
図表とレイアウトは**実際にA4へ印刷して目視で確認**するのが唯一確実な検証方法であり、
スナップショットは変更のたびに更新が必要になって形骸化しやすいためです。
開発時は Playwright で印刷PDFを生成して確認しています（手順は
[05_カスタマイズガイド.md](05_カスタマイズガイド.md) の第5節）。
