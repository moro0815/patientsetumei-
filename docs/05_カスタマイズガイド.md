# カスタマイズガイド

貴院の運用に合わせて内容を変更する方法です。

| 変更したいもの | 方法 | ビルド必要 |
| --- | --- | --- |
| 医療機関名・連絡先・運動教室の案内 | ⚙️ 設定画面 | 不要 |
| 文字サイズ・ふりがな・医師メモの表示 | ⚙️ 設定画面 | 不要 |
| 診療報酬の点数 | `src/data/fees.ts` | 必要 |
| 薬剤の商品名・費用・注意点 | `src/data/drugs.ts` | 必要 |
| 運動メニュー・処方量 | `src/data/exercises.ts` | 必要 |
| 栄養の目標量・生活指導 | `src/data/nutrition.ts` | 必要 |
| 説明スライドの文言・順序 | `src/slides/*.tsx` | 必要 |
| **症状別疾患の説明内容（腰・肩・足など12疾患）** | `src/data/conditions/*.tsx` | 必要 |
| トップ画面の並び・部位のグループ | `src/data/diseaseCatalog.ts` | 必要 |
| 図表 | `src/components/figures/*.tsx` | 必要 |
| パンフレットの構成 | `src/components/pamphlet/Pamphlet.tsx` | 必要 |

> **症状別の12疾患は、文章もスライドもパンフレットも `src/data/conditions/` の1ファイルにまとまっています。**
> 「この説明を変えたい」というときは、まずそこを探してください（第8節）。

ビルドが必要な変更のあとは：

```bash
npm test           # 臨床ロジックが壊れていないか確認
npm run build      # dist/ を再生成
# dist/ を配置し直す
```

## 1. 診療報酬の点数を更新する

`src/data/fees.ts`

```ts
// ① マスタ全体の最終確認日を更新する
export const FEE_MASTER_VERIFIED_AT = '2026-08-15'   // ← 確認した日付に

export const FEE_ITEMS: FeeItem[] = [
  {
    id: 'undouki-reha-1',
    code: 'H002',
    name: '運動器リハビリテーション料（Ⅰ）',
    points: 185,          // ← ② 最新の点数表の値に
    unit: '1単位（20分）',
    requirement: '...',   // ← ③ 算定要件が変わっていれば更新
    facilityStandard: '必要（施設基準の届出）',
    disease: ['osteoporosis', 'ra', 'kneeOA'],
    meta,
    sources: ['mhlw-fee-r8'],
  },
]
```

- `points: null` にすると、画面に「**要確認**」と表示されます。
  **確認できていない項目は、推測で数字を入れずに `null` にしてください。**
- 項目を追加した場合は、`src/logic/karte.ts` の `suggestFees()` で
  どの条件のときに候補として出すかを設定します。

### 算定候補の出し方を変える

`src/logic/karte.ts`

```ts
export function suggestFees(session: Session): FeeItem[] {
  const out: FeeItem[] = []

  // 例：運動器リハビリを導入したときだけリハ料を候補に出す
  if (session.plan.exercisePathway.includes('undoukiRehab')) {
    out.push(...FEE_ITEMS.filter((f) => f.id.startsWith('undouki-reha-')))
  }

  // 例：自院で新設した加算を、骨粗鬆症で薬を開始したときに出す
  if (session.disease === 'osteoporosis' && session.plan.drugIds.length > 0) {
    out.push(...FEE_ITEMS.filter((f) => f.id === 'my-clinic-kasan'))
  }
  // ...
}
```

### 分類による自動処理

`cls` に応じて、以下が自動で働きます（`src/data/drugs.ts` の末尾）。

| 分類 | 自動で起きること |
| --- | --- |
| `bisphosphonate` / `denosumab` / `romosozumab` | 歯科連携のスライドとパンフレットのページが追加され、カルテ文に顎骨壊死の説明が入る |
| `teriparatide` / `abaloparatide` / `romosozumab` | 逐次療法のスライドが追加され、「後続薬の予約確保」が今日のToDoに入る |
| `csdmard`（MTX） | 週1回カレンダーのスライド、血液検査のToDoが入る |

新しい分類を追加する場合は `src/types/index.ts` の `DrugClass` に追記します。

## 5. パンフレットの構成を変える

`src/components/pamphlet/Pamphlet.tsx`

### ページを追加する

1. `PamphletSection` に識別子を追加
2. `SECTION_LABELS` にラベルと説明を追加（選択ボタンになります）
3. `Pamphlet` の中に `{has('新しいID') && <MySheet session={session} />}` を追加
4. `MySheet` を実装

```tsx
function MySheet({ session }: { session: Session }) {
  return (
    <Sheet title="ページの見出し" page="セクション名">
      <PFig w={160} className="mb-3">
        <MyFigure />
      </PFig>
      <Box title="■ 見出し" tone="warn">
        <ul className="space-y-1">
          <li>・内容</li>
        </ul>
      </Box>
      <WriteLines n={3} label="■ 書き込み欄の見出し" />
    </Sheet>
  )
}
```

### 印刷レイアウトのコツ

| やりたいこと | 方法 |
| --- | --- |
| A4 1ページを1つの `Sheet` にする | `<Sheet>` が `break-after: page` を持っています |
| 途中で分割されたくないブロック | `avoid-break` クラス（`break-inside: avoid`） |
| 図が大きすぎてページに収まらない | `<PFig w={150}>` で幅の上限（mm）を指定。**図は幅を絞ると縦も短くなります** |
| 高さのばらつくカードを詰めて配置 | 親を `columns-2 gap-3`、子に `mb-3 break-inside-avoid`（grid より紙面が埋まります） |
| 印刷時だけ薄い背景を付ける | `print-fill-light` クラス |
| 画面だけ／印刷だけに出す | `no-print` / `print-only` クラス |

印刷用CSSは `src/index.css` の `@media print` にまとまっています。

### ページ数を確認する

ブラウザの印刷プレビューで確認できます。開発時は Playwright でも確認できます。

## 6. 取り込みで読み取れる項目名を増やす

「うちの問診システムは『疼痛関節数』ではなく『圧痛関節（28）』と出る」といった場合、
`src/logic/importer.ts` の `FIELDS` にラベルの別名を足すだけで読めるようになります。

```ts
{
  key: 'tenderJoints28',
  label: '圧痛関節数',
  aliases: [
    '圧痛関節数', '疼痛関節数', '圧痛関節', '圧痛', 'TJC28', 'TJC',
    '触診で痛い関節',
    '圧痛関節（28）',        // ← 貴院の問診システムの表記を追加
  ],
  kind: 'number',
  min: 0,
  max: 28,
}
```

### 追加するときの注意

1. **別名は「長い（specificな）ものから順に」並べてください。**
   `FIELDS` の並び順がそのままマッチの優先順位です。
   `CRP` を `DAS28-CRP` より先に置くと、`DAS28-CRP 4.45` を CRP 4.45 と誤読します。
2. **英数字だけの短い別名には `strict: true` を付けてください。**
   前後に英数字が続かないことを確認する境界が入ります。
3. **`min` / `max` を必ず設定してください。** 範囲外の値は取り込まず警告になります。
   これが誤読に対する最後の防波堤です。
4. **テストを先に書いてください。**

```ts
// src/logic/importer.test.ts
it('「圧痛関節（28）」を読み取れる', () => {
  expect(val('圧痛関節（28）：6', 'tenderJoints28')).toBe(6)
})
it('新しい別名が他の項目を誤読しない', () => {
  expect(val('圧痛関節（28）：6\nCRP 1.2', 'crp')).toBe(1.2)
})
```

### 新しい項目そのものを増やす

1. `ImportKey` に識別子を追加
2. `FIELDS` に定義を追加
3. `applyParsedFields` の `switch` に反映先を追加
4. `fieldsForDisease` の疾患ごとの許可リストに追加
5. URL連携でも渡したい場合は `src/logic/urlParams.ts` の `NUMERIC_PARAMS` と
   `URL_PARAM_DOC` にも追加

## 7. 問診システムとの連携を調整する

院内のデジタル問診システム（`monshin-tablet`）から直接読み込む処理は
`src/logic/monshin.ts` にまとまっています。**読み取り専用（GET のみ）**です。

### 問診の設問を増やしたときに取り込む

問診システム側で設問を足したら、`applyIntakeToSession()` にマッピングを1つ足します。

```ts
// src/logic/monshin.ts の applyIntakeToSession 内
// 例）「痛みで眠れない日数」を新設した場合
if (typeof a.sleepless === 'string' && a.sleepless) {
  ra.morningStiffness = ...   // 反映先（既存の欄か、types に新設した欄）
  applied.push('痛みで眠れない日数')
}
```

- 反映先の欄が無ければ `src/types/index.ts` の `RaInput` などに追加します
- カルテ記載にも出したい場合は `src/logic/karte.ts` に1行足します
- **プレビュー**（`MonshinPanel.tsx` の `PreviewList`）にも行を足すと、
  取り込む前に医師が確認できます

### 選択肢のラベルを変えたとき

「30分未満」「30分〜1時間」などの選択肢の文言を問診システム側で変えた場合、
`monshin.ts` の対応表（`STIFFNESS_LABEL` / `CHANGE_LABEL`）を合わせます。
対応表に無い値はそのまま文字列として入るため、**取り込み自体は壊れません。**

### 接続先・タイムアウト

| 設定 | 場所 | 既定 |
| --- | --- | --- |
| 問診システムのURL | ⚙️ 設定、または `src/data/clinic.ts` の `monshinBaseUrl` | 空文字（＝同一オリジン） |
| 連携機能の有効/無効 | `monshinEnabled` | `true` |
| タイムアウト | `src/logic/monshin.ts` の `AbortController` | 4秒 |

タイムアウトを長くすると、問診システムが落ちているときに診察が止まります。
**接続できないときは貼り付け取り込みへ誘導する**設計にしてあるため、短いままを推奨します。

### 疾患活動性のカットオフを変える

`src/data/clinic.ts` の `das28crpThresholds` を `'classic'`（慣用基準）と
`'crpAdjusted'`（CRP調整基準）で切り替えます。設定画面からも変更できます。

**変更する場合は、問診システム側（`js/doctor.js` の `raCatClass`）も必ず合わせてください。**
同じ患者の同じ値が2つの画面で違う区分になると、説明が破綻します。

計算式そのものは `src/logic/ra.test.ts` の「問診システムと計算式が一致すること」で
両システムの一致を検証しています。**どちらかの式を変えたらこのテストが落ちます。**

## 8. 疾患を追加する

### 8-1. 症状別疾患を足す（ふつうはこちら）

**画面のコードは1行も書きません。** 疾患の「中身」を書くだけで、
入力フォーム・判定パネル・説明スライド（14〜17枚）・パンフレット（3枚）・
カルテ記載文・算定候補が、すべて自動で生成されます。

**手順は3つだけです。**

```
① src/types/index.ts の ConditionKey にキーを1つ足す
② src/data/conditions/ のいずれかのファイルに ConditionDef を1つ書く
③ src/data/conditions/index.ts の CONDITIONS に1行足す
```

②で書く内容は、既存の疾患（例：`src/data/conditions/upperlimb.tsx` の `tennisElbow`）を
まるごとコピーして、中身を差し替えるのがいちばん早いです。

```ts
export const myCondition: ConditionDef = {
  key: 'myCondition',
  label: '正式な病名',
  subLabel: '患者さんの言い方（トップ画面のカードに出ます）',
  aka: ['別名', 'よくある言い方'],      // ← トップ画面の検索でヒットします
  icon: '🦵',
  accent: 'from-teal-50 to-teal-100 border-teal-300',
  region: '足',                          // 6つの部位のいずれか
  oneLiner: '患者さんへの一行説明。',

  // ---- 入力の選択肢（そのまま画面のチップになります）
  sideRelevant: true,
  duration: [{ id: '<1m', label: '1か月未満' }, ...],
  symptomOptions: [{ id: 'xxx', label: '患者さんの言葉', hint: '医師向けの補足' }, ...],
  findingOptions: [...],                 // 徒手検査・診察所見
  redFlagOptions: [...],                 // 選ばれると警告と紹介提案が出ます
  priorTreatmentOptions: [...],          // 治療の段の提案に使います
  stages: [...],                         // 任意。病期・重症度
  metrics: [...],                        // 任意。歩ける距離・可動域などの数値

  // ---- 説明の中身
  figure: (c) => <MyFigure severity={...} />,   // 病態の図（入力を反映できます）
  extraFigures: [...],                          // 任意。追加の図
  what: ['何が起きているか', ...],
  whyPain: ['なぜ痛いか', ...],
  mechanismTalk: ['医師用トーク', ...],
  course: { headline: '見通しの結論', points: [...], phases: [...] },
  treatments: [{ title: '第1段', points: [...], drugIds: [...] }, ...],
  exercise: { why: [...], recommendedIds: [...], cautions: [...] },
  selfCare: [...], avoid: [...], warnSigns: [...],
  workup: ['検査の考え方（医師向け）', ...],
  labIds: [...], nextVisit: '...', minutes: 4,
  sources: ['出典ID'],
}
```

**書いたあとは必ず `npm test` を実行してください。**
`src/logic/condition.test.ts` が、12＋1疾患すべてについて次を自動で確認します。

- `recommendedIds` の運動が実在し、**その疾患向けに登録されているか**
  （`src/data/exercises.ts` / `exercises2.ts` の `disease` にキーを足し忘れていないか）
- `drugIds` の薬剤、`labIds` の検査、`sources` の出典が実在するか
- 選択肢のIDが重複していないか
- レッドフラッグ・見通し・治療の段が1つ以上あるか

これらは画面を見ても気づきにくい間違いなので、テストで止める設計にしています。

### 8-2. 判定ロジックを持つ疾患を足す（骨粗鬆症・RAのような場合）

検査値から基準を当てはめる計算が必要な疾患は、専用のコードが必要です。

1. `src/types/index.ts` の `DiseaseKey` に追加し、入力の型を定義
2. `src/state/session.ts` の `createSession` に初期値を追加
3. 入力フォームを `src/screens/forms/` に作成し、`InputScreen.tsx` に接続
4. 判定ロジックを `src/logic/` に作成し、**テストを同時に書く**

## 9. 変更を安全に行うための順番

臨床判断のロジックを変えるときは、**テストを先に書き換えてください。**

```bash
# 1) テストに新しい基準を書く（この時点で失敗する）
vi src/logic/osteoporosis.test.ts
npx vitest run   # 失敗を確認

# 2) 実装を直す
vi src/logic/osteoporosis.ts
npx vitest run   # 全件成功を確認

# 3) 型と本番ビルド
npx tsc --noEmit -p tsconfig.app.json
npm run build

# 4) パンフレットを実際に1部印刷して目視確認
```

この順番にすると、**「基準を変えたつもりが別の条件を壊していた」**という事故を防げます。
実際にこのシステムの開発中も、立ち上がりテストの「立てない」と「未実施」の混同、
ACR/EULAR 2010分類基準の階層の取り違えを、テストが検出しました。
