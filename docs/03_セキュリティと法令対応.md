**このドキュメントは技術者向けのチェックリストです。導入前に管理者（院長・事務長）と確認してください。**

## 前提となる規程

| 規程 | 発行 | 位置づけ |
| --- | --- | --- |
| 医療情報システムの安全管理に関するガイドライン **第6.0版** | 厚生労働省（2023年5月、Q&A 2025年5月） | 医療機関が守るべき基準 |

| 個人情報の保護に関する法律／医療・介護関係事業者における個人情報の適切な取扱いのためのガイダンス | — | 要配慮個人情報としての取扱い |

## 1. 本システムが扱うデータ

| データ | どこに保持されるか | 既定の保存 |
| --- | --- | --- |
| 患者の氏名（任意入力） | ブラウザのメモリ内のみ | **保存しない** |
| 受付番号・年齢・性別・身長体重 | ブラウザのメモリ内のみ | **保存しない** |
| 検査値（骨密度・CRP・関節所見など） | ブラウザのメモリ内のみ | **保存しない** |
| 上記すべて（「一時保存」を押した場合） | `sessionStorage` | **タブを閉じると消える** |
| 医療機関設定・表示設定 | `localStorage` | 保存する（患者情報を含まない） |
| 実施記録（構成Cのみ） | 院内サーバーの SQLite | 氏名を保存しない。受付番号はハッシュ、年齢は5歳刻みの年齢層 |

### 設計上の重要な点

- **既定で患者情報がディスクに書かれません。** 説明が終われば端末には何も残りません。
- **外部への通信が一切ありません。** 外部CDN・外部フォント・分析タグ・エラー送信を含みません。
  `deploy/nginx.conf` の Content-Security-Policy で `connect-src 'self'` に制限しています。
- 印刷したパンフレットは**紙媒体の診療記録に準じた管理**が必要です（誤配布・置き忘れの防止）。

## 2. 構成別のリスクと対応

### 構成A：端末に置くだけ

| 論点 | 対応 |
| --- | --- |
| 端末の紛失・盗難 | ディスク全体の暗号化（BitLocker / FileVault）を有効にする |
| 画面の覗き見 | 説明用モニタの向き。待合から見えない配置にする |
| ブラウザに残るデータ | 患者情報は既定で保存されない。「一時保存」を使ったら診察後に「診察を終了」を押す |
| 共有アカウント | 端末のログインはスタッフごとに分ける（誰が操作したかを追えるようにする） |

### 構成B：院内サーバーで静的配信

上記に加えて：

| 論点 | 対応 |
| --- | --- |
| 外部からの到達 | **インターネットから到達できないネットワーク構成にする。** ルータでポートを開けない |
| 通信の盗聴 | 院内LANでも、無線を使う場合は WPA3（または WPA2-Enterprise）で保護する |
| なりすまし配信 | サーバーのIPを固定し、DHCPスヌーピング等の基本対策を行う |
| アクセスログ | nginx のアクセスログを保存する（誰がいつ開いたか）。保存期間を規程で定める |

### 構成C：院内サーバー＋API

上記に加えて：

| 論点 | 対応 |
| --- | --- |
| API の認証 | `SETSUMEI_TOKEN`（共有トークン）。**初期値のままでは起動しない設計**にしています |
| トークンの管理 | `openssl rand -hex 32` で生成。`.env` は Git にコミットしない（`.gitignore` 済み） |
| データの最小化 | 氏名を受け取らない。受付番号はソルト付き SHA-256、年齢は5歳刻みの年齢層で保存 |
| 保持期間 | `RECORD_RETENTION_DAYS`（既定5年）。超過分は起動時に自動削除 |
| バックアップ | 院内に限定。外部へ持ち出す場合は暗号化。**バックアップの復元試験を年1回行う** |
| 権限 | コンテナは非root（uid 1000）、`read_only: true`、`no-new-privileges` を設定済み |
| 監査 | 誰がマスタを更新したかの記録は本システムでは持ちません。**運用でトークンを管理者のみに限定してください** |

## 3. クラウド運用を検討する場合

将来の発展性としてクラウド運用は可能ですが、**院内完結より要件が大幅に増えます。**
以下をすべて満たせない場合は、院内サーバーでの運用を強くおすすめします。

### 事業者側に求めること（3省2ガイドライン）

- [ ] クラウド事業者が3省2ガイドラインへの適合を表明している（ISMAP登録の有無も確認）
- [ ] データセンターの所在地が国内であること（法適用と災害時対応の観点）
- [ ] 事業者との**委託契約**に、安全管理措置・再委託の制限・監査への協力・
      事故発生時の通知義務・契約終了時のデータ返還／消去を明記
- [ ] 事業者側の運用担当者がデータにアクセスできる範囲と、その記録の開示方法

### 医療機関側で実装すること

- [ ] **通信の暗号化**：TLS 1.2 以上（1.3推奨）。HSTS を設定
- [ ] **利用者認証**：ID/パスワードだけでは不十分。二要素認証（TOTP・クライアント証明書等）
- [ ] **アクセス制御**：職種ごとの権限分離（説明の実施／マスタ編集／集計閲覧）
- [ ] **アクセスログ**：本人特定できる形で操作記録を保存。改ざん検知と保存期間の規程
- [ ] **保存データの暗号化**：ストレージレベルの暗号化と鍵管理
- [ ] **IP制限**：院内の固定IPからのみ接続可能にする（VPN／専用線を推奨）
- [ ] **バックアップ**：地理的に分離した保管。復元試験の実施
- [ ] **インシデント対応手順**：発覚から報告までのフロー、個人情報保護委員会への報告体制
- [ ] **BCP**：クラウドが停止した場合に説明を継続する手順（`dist/` を端末に置いておく等）
- [ ] **医療情報システム安全管理責任者**の任命と、年1回以上の教育・訓練

### 本システム側で追加実装が必要なもの

現状のサーバー実装は**院内LAN前提**であり、クラウド運用には以下が不足しています。
クラウド化する場合は追加開発が必要です。

- 利用者ごとのアカウントと二要素認証（現在は共有トークンのみ）
- 操作ログの記録（誰がいつ何をしたか）
- ロールベースのアクセス制御
- TLS 終端（現状はリバースプロキシ側で行う想定）
- レート制限とブルートフォース対策

## 4. 運用開始前チェックリスト

### 技術

- [ ] `npm test` が全件成功する
- [ ] `npm run build` が成功し、`dist/` が生成される
- [ ] ブラウザの開発者ツールの Network タブで、**外部ホストへの通信が0件**であることを確認
- [ ] 構成C：`SETSUMEI_TOKEN` を推測されにくい値に変更した
- [ ] 構成C：`docker compose` の `ports` が `0.0.0.0` になっていない
- [ ] 構成B/C：インターネットから到達できないことを外部から確認した
- [ ] バックアップの取得と**復元**を1回試した

### 臨床コンテンツ

- [ ] 診療報酬の点数を院内で確認し、`src/data/fees.ts` を更新した
- [ ] 薬剤の商品名を院内採用品に置き換え、用量・禁忌を添付文書で確認した
- [ ] 運動処方の内容・強度を理学療法士が確認した
- [ ] パンフレットを実際に印刷し、医師・看護師・PTで内容を確認した
- [ ] ガイドラインの版が最新であることを確認した（[04_臨床コンテンツ出典.md](04_臨床コンテンツ出典.md)）

### 運用規程

- [ ] 印刷したパンフレットの取扱い（誤配布防止、不要分の廃棄方法）を決めた
- [ ] 端末のディスク暗号化とスクリーンロックを有効にした
- [ ] スタッフへの説明（このシステムは説明支援であり、診断を代替しないこと）を行った
- [ ] 患者さんから「この資料は誰が作ったのか」と聞かれたときの回答を統一した

## 5. インシデント時の初動

| 事象 | 初動 |
| --- | --- |
| 端末を紛失した | ディスク暗号化の有効性を確認。患者情報は既定で保存されないが、`sessionStorage` に残っていた可能性を評価 |
| パンフレットを患者さんに誤って渡した | 回収を試み、記録を残す。個人情報漏えいとしての報告要否を管理者が判断 |
| サーバーに不審なアクセスがあった | ネットワークから隔離 → ログを保全 → `SETSUMEI_TOKEN` を再生成 → 影響範囲を評価 |
| 誤った臨床情報が印刷された | 該当箇所を特定して修正 → 影響を受けた患者さんへの説明 → マスタ確認手順の見直し |
